# Contributing to draftwright

Contributions are welcome: bug reports, fixes, features and documentation.

## Contributor License Agreement

draftwright is released under the AGPL-3.0 and is also offered under separate
commercial terms by the copyright owner. So that contributions can be included
in both, every contributor agrees to the
[Contributor License Agreement](CLA.md). You keep the copyright to your work;
the CLA grants a licence, not an assignment.

On your first pull request a bot asks you to sign by replying:

> I have read the CLA Document and I hereby sign the CLA

Pull requests cannot merge until the CLA is signed.

## Test files and data

Add only files you created yourself or whose licence allows redistribution, and record each
file's source and licence beside it (a fixture README or NOTICE entry). Never add customer,
confidential or NDA-covered files, or geometry extracted from them, to the repository, to
issues or to pull requests. For a bug seen on such a part, share a reduced synthetic part that
reproduces it instead.

## Local tests and CI tiers

Run the full local workspace suite (including doc-tests and the whole-binary drawing
harnesses) with the shared disk cache enabled:

```sh
DRAFTWRIGHT_CORPUS=/path/to/quiddity/tests/corpus DRAFTWRIGHT_CORPUS_REQUIRED=1 DRAFTWRIGHT_TEST_PLAN_CACHE="$PWD/target/test-plan-cache" cargo test --workspace --release
```

Use the pinned corpus revision from `ci.yml`. The first run fills the cache; subsequent
processes and runs reuse native analyses and default plans. `src/plan_cache.rs::key`
includes `DRAFTWRIGHT_ENGINE_VERSION`, generated by `build.rs` / `build_support.rs` from
engine sources, schemas, fonts, the root manifest and lockfile, as well as platform, profile and
all cache inputs. Rebuilding after an engine change therefore cannot read stale entries.
There is no lock around full-suite runs; the existing cache only coordinates individual
entries. Local latency assertions stay enabled.

- **PR:** lint, build and doc-tests, two duration-balanced shards containing every test
  recorded at **at most 10 seconds** plus every unrecorded test, and the whole
  `issue_drafting`, `issue_trust` and `steerability` harnesses. Two acceptance shards measure
  all 68 unpinned quality/AP242/survey parts, and quality-gate enforces the drawing baseline, crossings,
  routes, label lanes and repeated spans. This is **10 jobs**, down from 22; the target is
  roughly **10–12 minutes** with warm build caches, subject to runner queues and new tests' durations. Two shards
  leave headroom for process startup and unrecorded tests; one would carry about 34
  estimated test-minutes before that overhead. Relevant WASM/API/binding changes also
  run the cheap WASM safeguard unit tests in lint; generated API and size checks require
  the full WASM build and remain in the full tier.
- **Main:** every push runs the full ten balanced shards, harnesses, all acceptance jobs
  (including budgets) and browser WASM parity: **22 jobs**, roughly **25 minutes**.
  The full nine-cell random-pin sweep (270 additional drawings), budgets and WASM are
  deferred on ordinary PRs to save runners. CI asserts that the PR
  tier plus recorded slow tests partitions the main nextest selection.
- **Full on demand:** add the **`full-ci`** label to a PR (also applies to subsequent
  pushes), or run the **CI** workflow with **Run workflow** on the desired ref. Both run
  the same full tier as main. Removing the label restores the fast tier.
- **Release:** the exact tagged commit must have successful **full push-to-main CI**
  before any CLI/WASM assets or crates.io/PyPI packages are published. The release guard
  checks the latest result of every full-tier job, including carried-over rerun successes; PR/dispatch success or a historic
  lint-only run does not qualify. The **Pre-publication tests** workflow runs the five
  `release-only` nextest checks once for the release event. All four publishers wait
  for the same first attempt on the tagged commit.

Counts above cover `ci.yml`; the existing path-filtered wheel,
crate-package and CLI workflows retain their own PR checks. Hosted wall times are estimates, not measured here.

### Professional drawing benchmark

With a release CLI and the public corpus, run:

```sh
export DRAFTWRIGHT_CORPUS=/path/to/quiddity/tests/corpus
export REF=/path/to/nist-ref
python3 -I tools/pro_benchmark.py --binary target/release/draftwright
```

Download the semantic PMI STEP AP242 exports for CTC01–05 and FTC06–11 from
[NIST's CAD and STEP downloads](https://www.nist.gov/ctl/smart-connected-systems-division/smart-connected-manufacturing-systems-group/mbe-pmi-0).
Unpack one AP242 export per case into `$REF/ap242` or pass its directory
explicitly with `--nist DIR`.

Use `--json OUT` for the same counts in JSON and `--parts ctc_01 ftc_06` to
select cases and skip the independent 30-part gate. A full run uses
`tools/quality.py` and the maintained CI quality baseline. The benchmark
uses `DRAFTWRIGHT_PLAN_CACHE` for public inputs when set.
Cost is the sum of draftwright child-process instructions retired, collected
with `/usr/bin/time -l` on macOS when the host exposes the counter. Other
environments report n/a.

The source-PMI row measures the share of inventoried STEP requirements drawn
and verified by draftwright's fidelity checks. It separately counts drawn
requirements with fidelity failures and absent requirements. For the latter,
it counts sources that review reports as not drawn through omission findings.
The NIST FTC workbook, specification indexes and SFA records describe the
public reference cases. Their construct and analyzer counts are separate from
the source audit, since an annotated export and a geometry-only export do
not carry the same requirements.

Completeness includes every recognized feature and uses draftwright's own
findings. A feature with no sizing or locating failure counts as complete.
Features the planner exempts from drafting by design are counted separately.
An exempt feature also needs explicit rendered measurement claims on its own
feature ID for both a size and a location. Sizing and locating findings count
once per affected feature, including
`feature_not_dimensioned`, `feature_not_sized`, `feature_not_located`,
`dimensions_not_ported`, the feature requirement failures and the additional
codes in `FEATURE_GAPS`. The true-view row counts only inclined holes and
bosses with the inclined-axis location variant of `feature_not_dimensioned`
and no rendered view along the feature axis. Its denominator gives the total
recognized feature count for context. Redundancy counts `duplicate_measurement`,
`closed_dimension_chain`, `feature_located_twice` and `over_dimensioned_pattern`.

Set `DRAFTWRIGHT_BENCH_PRIVATE` to run local human references alongside NIST.
The tool's docstring defines the manifest and reference schema. The private
report uses opaque case IDs and counts, and the private plan cache is temporary.
Dimension presence includes automatic dimensions and drawn Spec-authored
control frames. It requires the reference feature, kind, nominal and ordered
datum references. Linear and thickness dimensions can match each other. A
datum reference needs STEP PMI or a Spec datum used by the drawing. A geometry-only
part with no Spec cannot satisfy a datum-referenced dimension. Both dimension
rows show separate counts for datum-referenced and toleranced-only dimensions.
The agreement row uses the same denominator and also requires any specified
tolerance or fit.

## Releasing

Publish a release only after main CI is green; the guard waits up to 45 minutes for a run in progress.

For a backfill without an automatic gate run, dispatch **Pre-publication tests** on main
with the existing tag and its full commit SHA. Use that run's ID in `release_checks_run`
when manually dispatching each publisher. To recover from a failed gate, use the same
successful `run ID/attempt` for all manual publishing runs.

The repository is `pzfreo/draftwright`; `pzfreo/draftwright-python` is the earlier
Python implementation, being retired.

The current release is 0.6.0-alpha.2; 0.6.0 is in alpha (pre-release). The release commit
updates the native, WASM and Python-extension Cargo versions together, `Cargo.lock`,
README status and CHANGELOG. Wheel packaging lives in the root
`pyproject.toml`, using maturin's `bindings = "pyo3"`, the unpublished
`crates/draftwright-py` manifest and a dynamic Cargo-derived version. The mixed
package lives in `python/draftwright`; the extension is `draftwright._native`
(abi3, Python 3.9+). PyO3 must remain outside the published native crate and WASM
dependency graphs.
The Cargo versions remain at the current release until that coordinated release commit.
There is no separate wheel version to bump: release tag `vX.Y.Z`, Cargo version `X.Y.Z`
and every wheel's METADATA version `X.Y.Z` must agree. PyPI publishing uses 0.6.0 and its pre-releases.

Run formatting, strict release workspace/all-target Clippy, library tests and the full
required-corpus workspace nextest suite before releasing. Build the local wheel with
`RUSTC_WRAPPER= CARGO_BUILD_JOBS=6 uv tool run maturin build --release --locked`, install it
in a clean venv, and run `python -m unittest discover -s tests/python -v`.
Also run those tests with build123d installed to cover shape export and `source=`. No build outputs are committed.

Publishing a GitHub release drives the existing CLI archive, browser WASM and crates.io
workflows. `.github/workflows/publish.yml` additionally builds and smoke-tests mixed Python/Rust wheels
for macOS Intel/Apple silicon, manylinux 2_28 x86_64/aarch64 and Windows x86_64. We omit an
sdist: these installs should not unexpectedly require Rust on unsupported platforms.
The wheel workflow also runs for relevant main pushes and PRs; a manual run on main can
request publishing with `publish: true` and an explicit `tag`, such as `v0.6.0`.
Dispatch and release builds check out that tag, including in the publish job. Pre-release
tags must agree with the GitHub release's pre-release flag; pre-release wheels are published
too. Each wheel artifact includes its build commit in a separate
provenance directory; this directory is checked but never uploaded to PyPI.
`tools/check_wheel_versions.py` checks that the tag exists, HEAD and every wheel's build
commit match the tag's commit, and all three Cargo manifests and all downloaded wheels agree
before the trusted-publishing action runs. A missing/invalid tag, absent wheels or provenance,
or any commit/version mismatch fails the job. Versions before 0.6.0 are ineligible for PyPI publication.
`python3 tools/test_wheel_versions.py -v` exercises the guard's
success and refusal paths, including annotated tags. Publishing runs for the same tag are
serialized; existing PyPI files are skipped on reruns. No version mapping is used.

Trusted publishing uses owner `pzfreo`, repository `draftwright`, workflow `publish.yml`,
environment `pypi`. The existing trusted publisher should match after the rename — check it
on pypi.org. The publish action obtains an OIDC token (`id-token: write`); no stored token or
TestPyPI job is used. Build jobs have only read access. A local check must never publish.
